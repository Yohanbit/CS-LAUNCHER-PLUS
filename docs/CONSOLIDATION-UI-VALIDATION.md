## Cambios
1. **UI01: SettingsSaveManager + SharedSettings + Fragment.** Todos los controles (switch, slider, número exacto, dropdown e input) registran su clave sucia. El commit central importa shared ajeno, publica únicamente los valores de las claves editadas (también removals), escribe solo esas claves en main y recién después carga preferencias. Sin claves sucias, pause/destroy/Save no escriben un snapshot viejo. Los errores conservan dirty keys para retry, sin marcar éxito. `saveToMain` pasa por esa ruta. El antiguo botón Save tampoco publica un draft completo. Se registró explícitamente `perfModeMaximumAck`, antes persistido incidentalmente por bulk save. Presets escriben y publican el conjunto de sus claves antes de load; GIF actions también usan la ruta central, manteniendo controles existentes.

   **Afinamiento de auditoría:** switches y sliders YA espejaban individualmente antes del autosave. No eran universalmente revertidos: el rollback directo afectaba dropdown/input; además el bulk lifecycle guardaba un draft potencialmente viejo. La ruta de presets tenía publicación después de load, por lo que la política en memoria podía estar ya revertida.
2. **UI02: reset central.** Borra preferencias draft/main y únicamente `SharedSettings.SHARED_KEYS` del JSON compartido, preservando servidor/estado ajeno. Cancela pending edits. `CrossProcessState.mergeReset` filtra bajo el mismo FileLock y refresca el backup con el estado saneado, evitando resurrección después de corrupción. Un marcador interno `__sharedSettingsReset` impide bootstrap de defaults/caché pre-reset; los procesos que vuelven a sync eliminan claves shared ausentes tras reset. Nuevas elecciones explícitas se pueden publicar normalmente. La UI muestra fracaso si falla IO y solo recrea tras éxito.
3. **UI03: descripción experimental.** Scheduler bounded nice −2 y G1 compatible en Performance/Maximum, glthread Mesa donde corresponda; Extreme conserva GC ergonómico/no boost, Normal ignora el gate. Elimina promesas de heap/code-cache/young-generation ya retiradas. Maximum warning aclara que requiere opt-in. Javadoc PerformanceMode distingue `fromKey(null)`→Normal de preferencia ausente→default persistido Extreme; no altera defaults.
4. **UI04: texto honesto, no nuevo sampler/listener.** Enabling CSV/submission sampling empieza en próximo resume; GC logging requiere próximo JVM launch. No anuncia live ON que el código no implementa. OFF/cleanup existente se conserva.
5. **UI05: DRS live.** Descripción en primer plano; conserva restauración OFF, HUD escalado, métrica no-GPU y ausencia de pruebas físicas. No cambia el controller.
6. **UI06: pico térmico por Session.** FrameSampleCollector acumula máximo durante ticks y captura el pico del governor antes de pause/stop. Persist usa el máximo guardado, no solo el último foreground tras reset del governor. Resume misma Session conserva máximo; sesión nueva crea campo limpio. No cambia thermal polling ni simula temperatura física.
7. **UI07: RAM card.** Ambos cards Game/legacy Java leen draft, dicen Requested heap y advierten que validación/argumentos JVM pueden cambiar el efectivo. Slider/número exacto y presets reconstruyen las categorías para actualizar el card. No modifica Tools ni cálculo runtime.
8. **Nuevo opt-in viable:** checkbox `experimentalModWorkarounds`, default false, en Experimental/Advanced, «Next launch»; explica desactivar checks de seguridad de mods/mixin seleccionados, riesgos de crash/ocultar incompatibilidad y uso limitado a modpacks afectados. **Runtime es propietario del field/read/argument wiring** con esa misma key; este cambio UI no afirma haberlo implementado.

## Límites e integración
- No ejecución física de Minecraft, medida FPS/temperatura, prueba de paquete/firma o build APK. Mantener target release 1.5.0 y paquete/firma; eso lo atiende parent. Defaults existentes preservados: preferencia ausente usa Extreme; valor inválido/fromKey(null) usa Normal. No se recomienda cambiar el perfil default.
- ADPF permanece desactivado; no se tocó policy ni se inventó medición CPU. Scheduler/G1/glthread/DRS/pacing y demás controles se conservan.
- No cambios Tools/JREUtils/Architecture/LauncherPreferences/resources XML. Textos afectados eran inline Java; no hizo falta strings.
- La prueba loader usa un double que reproduce su contrato sync-first; no compila toda LauncherPreferences ni verifica argumentos runtime. El merge garantiza aislamiento por **claves distintas**; una misma clave editada explícitamente por ambos procesos sigue last-writer-wins. Reset + preferencias + JSON no es una transacción única frente a kill/IO failure; se reporta failure y se puede reintentar.
- API no-arg commit ahora solo publica claves registradas. Call sites vistos: Fragment y saveToMain. La suite incluye scan de todos los archivos Java/Kotlin del checkout completo CI: excepciones de producción únicamente SettingsSaveManager propio y Fragment; fixtures tools se listan aparte. Cualquier referencia nueva (también static import o consumidor que solo obtiene draft) falla CI hasta revisión/coverage. No usar whole-draft mirror como fallback, pues reintroduciría el bug. El árbol source local es parcial; el resultado local no sustituye al scan CI del checkout completo.
- Thermal peak conserva el significado existente de nivel ordinal del foreground governor, no °C ni atribución causal por renderer. Los splits por metadata dentro de un mismo foreground todavía pueden compartir el pico de ese tramo; no se anunciaron como mediciones térmicas aisladas.
